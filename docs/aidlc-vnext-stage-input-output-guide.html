AI-DLC vNext · BEGINNER'S COMPLETE GUIDE

10個のステージと
入力・出力をゼロから理解する

AI-DLC vNextは、開発を10個の決められた区間に分けます。各区間は、前の区間で確定した情報を入力として受け取り、検証済みの成果物を出力します。この資料だけで全体を追えるように、専門用語を一つずつ説明します。

この資料は会話中の説明ではなく、現在の固定Stage Catalog、Stage Graph、各Stage Contract、TypeScript実装を読み直して作成しています。

最初に理解すること

「入力」と「出力」は、単なるファイルの受け渡しではありません。AIが思いつきで先へ進まないように、どの事実を使い、何を確定したかを残す仕組みです。

開始時の入力Stageを始める前に、すでに確定している事実です。
作業依頼Coreが入力から作る、AIへの範囲限定された指示書です。
AIの提案まだ正式成果物ではありません。Coreの検証を受けます。
正式な出力検証・承認後にCoreが保存する正本です。

3者の役割

AI調査し、案を作り、指定された形式でCoreへ提出します。次のStageは選びません。
Core固定Graphを管理し、入力・提案・承認・SHA-256を検証して、正式成果物と遷移を記録します。
人間価値判断、承認、Feedback、Release権限、Outcomeの受け止めを決めます。
すべてのStageに共通する裏側の入力
図に書かれた業務成果物とは別に、Coreは常にState、Stage Execution Plan、固定Catalog、固定Graph、Effective Policy、Audit、Workspace lockの整合性を確認します。

Stageは飛ばすのか

10個のStageそのものは固定です。Planは各Stageに「新しく作る」「承認済みのものを再利用する」「今回には該当しないと証明する」のいずれかを記録します。ただし、どの方法を使えるかは各Stage Contractが決め、必須Stageはnot_applicableを拒否します。小さな変更は、Stageを消すのではなく、必要な入力・出力が小さくなります。

通常は左から右へ進みます。ST-07で人間が変更を求めた場合だけ、影響が始まる最も早いStageへ戻ります。

ST-00

Bootstrap

AIが作業を始める前に、土台が壊れていないか点検する。

初心者向けの一言: 「このプロジェクトで安全に作業を始めてよいか」をCoreが機械的に確認する受付です。

入力

  • Stage Execution Plan — 10 Stageをどう扱うかのCore計画
  • vNext State — 現在地と状態
  • Effective Policy — 組織・チーム・プロジェクトの追加ルール
→

正式な出力

  • Bootstrap Receipt — 何を確認し、すべて通ったかを示す点検記録

Stage内の処理

Intent、Space、Workspaceを確認
Catalog、Graph、Plan、Policy、Repositoryを確認
Receiptを保存し、ST-01へ進める

人間が必要になる場面

通常は不要です。欠落、改ざん、読めないRepositoryなどの例外がある場合だけ、人間へ戻します。

主な保存先

artifacts/bootstrap-receipt-r1.json
↑ 先頭へ
ST-01

Orient

今回必要な範囲の「現在のシステム」をEvidence付きで把握する。

初心者向けの一言: 地図を見ずに改修を始めないため、現在のコード・構成・関係を確認します。全世界を毎回調べるのではなく、今回必要な範囲を観測して共有地図へ積み上げます。

入力

  • Design Brief — 最初に渡された依頼の概要
  • Bootstrap Receipt — 開始点検に合格した証拠
  • Effective Policy — 調査時に守るルール
  • 既存System Map baseline — 以前までの共有地図。なければ新規作成
→

正式な出力

  • Workspace Profile — 対象Repositoryとsnapshot
  • System Map — Evidence付きの累積的な現在観測Map
  • System Map Baseline — 現在の共有revisionを示すポインタ
  • Current Context — 今回のIntentが使うMap範囲とrevisionの固定参照

Stage内の作業用成果物

Coreがorient-work-request.jsonを作る
AIがSystem Map PatchとContext候補を提案
Coreがpath、SHA-256、ID、relation、freshnessを検証

observedunobservedstaleunknown を区別し、不完全な地図を「完全」と誤認しないようにします。

人間が必要になる場面

通常は不要です。対象Repositoryが不明、Evidenceが取れない、秘密情報を含むなどの例外時だけ確認します。

主な保存先

aidlc/spaces/<space>/codekb/system-map/
artifacts/current-context.json
重要: System Mapの正本はJSONです。通常はHTMLを作りません。Current Contextは使ったMap revisionとSHA-256を固定するため、後で共有Mapが更新されても過去Intentの根拠は変わりません。
↑ 先頭へ
ST-02

Define Intent

今回の仕事の目的と境界を短く、はっきり定義する。

初心者向けの一言: 「何を作るか」の前に、「何のために、どこまでを、どうなれば成功とするか」を合意できる形にします。

入力

  • Design Brief — 元の依頼
  • Current Context — 現在の事実と対象範囲
  • Effective Policy — 守るべき追加ルール
→

正式な出力

  • Intent Definition
    • 目的
    • 期待する結果
    • 対象／対象外
    • 成功の見方
    • 既知の不明点

Stage内の処理

Coreが入力を固定したWork Requestを作る
AIがIntent Definition Proposalを作る
Coreが範囲の矛盾や後続設計の混入を拒否する

人間が必要になる場面

優先順位、価値判断、目的の曖昧さが入力から決められない場合は、AIが人間へ質問します。

主な保存先

artifacts/intent-definition.json
ここではまだ決めない: 詳細要求、Architecture、API設計、実装手順、Bolt、次のStageは書きません。
↑ 先頭へ
ST-03

Requirements & Constraints

目的を、追跡可能で確認できる要求と制約へ変える。

初心者向けの一言: 「こうなってほしい」を、後で合否を判断できる約束へ変えます。

入力

  • Intent Definition — 目的・範囲・成功の見方
  • Current Context — 対象の現在事実
  • Effective Policy — 品質・セキュリティ等のルール
  • 既存Requirements — revision更新時のみ任意
→

正式な出力

  • Requirements Definition revision
    • 機能要求
    • 品質要求
    • 制約
    • 常に守る不変条件
    • 未解決質問
  • Requirements Current — 現在採用するrevisionへのポインタ

Stage内の処理

Coreが目的・成功signalのcoverageを要求
AIが安定IDと根拠pointer付きで提案
Coreが重複、抜け、参照切れ、blocking questionを検証

各要求は、どの入力のどの項目から来たのかをJSON Pointerで追跡できます。

人間が必要になる場面

要求同士の衝突、優先順位、Policy例外、リスク受容、blocking questionが残る場合です。

主な保存先

artifacts/requirements/revisions/000001/requirements.json
artifacts/requirements/current.json
ここではまだ決めない: 技術構成、実装方式、テストコマンド、Bolt、Stage遷移は含めません。
↑ 先頭へ
ST-04

Architecture Decision

要求を満たすために、システム構造を変える必要があるか判断する。

初心者向けの一言: 「どの部品をどう組み替えるか」という大きな設計判断を扱います。現在の地図と将来案は混ぜません。

入力

  • Requirements Definition／Current
  • Current Context
  • System Map — 現在像
  • Effective Policy
  • 既存Architecture Decision — 再利用時は任意
  • Human Decision — 再利用承認時は任意
→

正式な出力

  • Architecture Current — 今回採用した処理と参照先
  • Architecture Decision revision — 新しい構造判断が必要な場合だけ作成
  • Policy Approval — Policyが要求した場合だけ

3つの処理方法

execute新しいArchitecture Decisionを作る　reuse既存の承認済み判断を再利用する　not_applicable構造への影響がないことを全要求について証明する

全Requirementを1回ずつ影響評価
AIが現在entity参照とplanned changesを提案
Coreがcoverage、Evidence、承認を検証

人間が必要になる場面

Provider、費用、データ移行、破壊的変更、Security／Compliance例外、戻しにくい判断、Policy Gate、既存判断の再利用承認です。

主な保存先

artifacts/architecture/current.json
artifacts/architecture/revisions/000001/architecture-decision.json
HTMLの扱い: 通常のArchitecture成果物はJSONです。Policy上の人間判断が必要なときだけarchitecture-policy-review.htmlを生成します。
↑ 先頭へ
ST-05

Build Contract

何を、どの単位で、どう検証して作るかを人間と合意する。

初心者向けの一言: 実装を始める直前の契約書です。変更対象、合格条件、検証方法、作業の依存関係を固定します。

入力

  • Requirements Definition／Current
  • Architecture Current／Decision
  • Current Context／System Map
  • Effective Policy
  • 既存Build Contract／Human Decision — 再利用時などに任意
→

正式な出力

  • Build Contract Candidate — 承認待ち候補
  • Build Contract Review HTML — 人間向け確認画面
  • Human Decision — SHA-256に結び付いた承認
  • Build Contract Current
  • Build Contract revision — execute時

Build Contractに入るもの

変更Contractと受入条件
Verifierと正確なargv／cwd
依存関係付きBolt DAGと統合条件

CoreはDAGの循環、Repository境界、並列target衝突、要求coverageを検査し、実行batchを導出します。AIはbatchや次のBoltを選びません。

人間が必要になる場面

このStageは重要な承認境界です。人間はReview HTMLで対象file、合格条件、Verifier、Bolt関係を確認し、候補のSHA-256へ承認または修正依頼を出します。

主な保存先

artifacts/build-contract/review/build-contract-review.html
artifacts/build-contract/revisions/000001/build-contract.json
まだ実装しません: ST-05ではテストコマンドも実行しません。実装と実行は人間承認後のST-06です。
↑ 先頭へ
ST-06

Build & Converge

承認済みContractどおりに、一つずつBoltを実装・検証する。

初心者向けの一言: ここが実際にコードを作るStageです。ただしAIが好きな場所から始めず、Coreが依存関係から「次の1 Bolt」を指定します。

入力

  • Build Contract Current／Build Contract
  • ST-05 Human Decision — 承認の証拠
  • Effective Policy
  • System Map — accepted source revision
  • 既存Runnable Candidate — 正確な再利用時のみ任意
→

正式な出力

  • Build Session
  • Bolt Work Request
  • Attempt Checkpoint
  • Verifier Evidence
  • Runnable Candidate — 全Boltと統合検証が通った候補
  • Build Current

反復の流れ

CoreがreadyなBoltを1つ選び、隔離Git worktreeを作る
AIが指定targetだけを変更する
Coreが変更pathとVerifierを確認し、合格まで同じBoltを再試行

全Boltが通った後に統合Verifierを実行し、初めてRunnable Candidateを作ります。同じ失敗が3回続く場合は停止します。

人間が必要になる場面

通常の実装反復では不要です。Contract矛盾、破壊的操作、外部作用、credential、base drift、収束不能などの例外で停止します。

主な保存先

artifacts/build/build-session.json
artifacts/build/bolts/<bolt-id>/...
artifacts/build/runnable-candidate.json
実装なしの場合: Build Contract Currentがnot_applicableなら、Git操作もRunnable Candidate作成も行わず、理由付きBuild Currentだけを記録します。
↑ 先頭へ
ST-07

Human Feedback & Approval

動く候補を人間が確認し、承認または具体的なFeedbackを返す。

初心者向けの一言: 機械テストだけでは判断できない「本当に意図どおりか」を、人間が実物と説明を見て判断します。

入力

  • Build Current／Runnable Candidate
  • Requirements Definition
  • Architecture Current
  • Build Contract
  • Effective Policy／System Map
  • Human Decision — Stage中に受け取る承認またはFeedback
→

正式な出力

  • Review Manifest／Review HTML
  • Human Decision
  • Accepted Candidate — 承認時
  • Feedback Current — 修正依頼時
  • Review Current — Stageの結論
  • 更新System Map — 承認sourceの昇格

人間の2つの選択

Approve
全human checkを満たし、exact candidateを承認
Request changes
Requirement IDと影響種別を付けてFeedback
Coreが承認ならST-08、Feedbackなら固定ルールで戻り先を決める

要求変更 → ST-03構成影響 → ST-04製造契約影響 → ST-05候補の不具合 → ST-06

人間が必要になる場面

ここでは必ず人間の明示判断が中心です。AIは承認を推測せず、戻り先も選びません。

主な保存先

artifacts/review/review.html
artifacts/review/human-decision.json
artifacts/review/accepted-candidate.json
実装なしの場合: ST-06にRunnable Candidateがない場合はReviewを重複実行せず、ST-05の「実装なし」承認をEvidenceとして決定的に通過します。
↑ 先頭へ
ST-08

Release

人間が承認した候補だけを、承認済み手順で外部環境へ反映する。

初心者向けの一言: 「作れた」から「利用できる場所へ出した」へ進むStageです。外部への変更なので、計画と権限を厳密に分けます。

入力

  • Review Current — ST-07の結論
  • Accepted Candidate — 候補がある場合
  • Effective Policy
  • Release Capability Snapshot — 実行可能な安全な操作
  • Deployment Map — 既存の配備状態
  • Release Authority — 実行前の人間権限
→

正式な出力

  • Release Work Request／Plan
  • Release Review HTML
  • Release Authority
  • Step Receipts／Release Receipt
  • Release Current
  • Deployment Map revision — 外部の配備状態

外部作用を安全にする順序

Coreがcapabilityと現在target状態を観測
exact PlanとrollbackをHTMLで人間へ提示
人間のAuthority後だけ実行し、各作用をReceiptへ記録

Targetが承認後に変わった場合は実行しません。結果が曖昧な外部操作を、重複の危険を冒して再実行しません。

人間が必要になる場面

外部へ変更を加えるRelease Planには、PlanのSHA-256と観測済みtarget状態に結び付いた明示的Release Authorityが必要です。

主な保存先

artifacts/release/release-plan.json
artifacts/release/review/release.html
aidlc/spaces/<space>/codekb/deployment-map/
rollbackも記録対象: Release失敗後に安全に戻せた場合も、「何もなかった」ことにはしません。rolled backという結果をReceiptとRelease Currentへ残します。
↑ 先頭へ
ST-09

Outcome Evaluation

作ったものではなく、最初に狙った結果が得られたか確認する。

初心者向けの一言: 「Releaseできた」だけで成功とは呼びません。最初の目的・成功signalと、実際のEvidenceを一つずつ比較してIntentを閉じます。

入力

  • Intent Definition — 期待した結果と成功signal
  • Requirements Definition
  • Review Manifest — Candidateがあった場合
  • Release Current — released／rolled_back／not_applicableを区別
  • Effective Policy
→

正式な出力

  • Outcome Work Request
  • Outcome Evidence
  • Outcome Evaluation
  • Outcome HTML
  • Outcome Human Decision — 必要時
  • Outcome Current
  • Follow-up Brief — 選択時だけ。新Intentは自動作成しない

完了の決め方

Coreが全Outcome、signal、Requirement、受入条件を固定
各signalへ検証済みEvidenceを1つ以上対応
全達成かつ追加Human Gateなしなら自動完了。それ以外は人間が誠実な終わり方を選ぶ

continue-observationcomplete-with-outcomecomplete-and-draft-follow-up

人間が必要になる場面

partial、failed、inconclusive、rolled backの場合です。観測を続けるか、現結果で完了するか、Follow-up Briefも作るかを決めます。

主な保存先

artifacts/outcome/outcome-evaluation.json
artifacts/outcome/outcome.html
artifacts/outcome/current.json
終端Stage: ST-09の後に次のStageはありません。CoreはOutcomeと完了理由を保存してIntent Stateをcompletedにします。Follow-up Briefは次の相談材料であり、AIが勝手に新Intentを作ることはありません。

どの出力がJSONで、どれがHTMLか

JSONは機械が検証する正本です。HTMLは人間が判断しやすくする表示です。HTMLだけを正本にはしません。

対象通常の形式HTMLを作る条件
System Map／Current ContextJSONSystem Map HTMLは人間が明示的に依頼した場合だけ
Intent Definition／RequirementsJSON標準では作らない
ArchitectureJSONPolicyによる人間判断が必要な場合
Build ContractJSON＋Review HTML人間承認のため必ずReviewを作る
Candidate ReviewJSON＋Review HTMLRunnable Candidateを人間が確認するとき
ReleaseJSON＋Release HTML外部作用の計画を人間が承認するとき
OutcomeJSON＋Outcome HTML結果を人間が読み、必要なら判断するとき

初心者向け用語集

Artifact

Stageが読み書きする成果物です。path、version、SHA-256で「どの内容か」を固定します。

Evidence

判断を裏付ける証拠です。file、検証結果、外部観測、人間確認などがあります。

Current

そのIntentが現在採用している結論やrevisionを指す小さな正本です。

Revision

上書きしない履歴番号です。過去の判断を後から確認できます。

SHA-256

内容から作る指紋です。承認後に内容が変わっていないことを確認します。

System Map

Repository、Component、API、Database、外部Service、関係をEvidence付きで累積する現在観測Mapです。

Effective Policy

Org、Team、Projectの機械実行可能な追加ルールを、固定優先順で統合したsnapshotです。

Bolt

ST-05で決める実装単位です。依存関係DAGに従い、ST-06でCoreが一つずつ選びます。

Candidate

検証には通ったが、人間承認やReleaseがまだの候補です。RunnableとAcceptedを区別します。

Receipt

機械点検や外部操作が実際にどう終わったかを残す記録です。

Core Directive

CoreがCodexへ返す次の行動です。work、approval、decision、advanced、parked、doneがあります。

fail closed

不明・不整合・改ざん時に推測して進まず、安全側で停止する考え方です。

全体を一文で: 前のStageの検証済み出力を次のStageの入力にし、AIは案を作り、Coreは正本と遷移を管理し、人間は価値・承認・外部作用・成果を判断します。
