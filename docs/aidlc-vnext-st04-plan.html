ST-04で決めるのは、
「システムの作り方」です。

ST-03で「何を満たすか」が決まりました。ST-04では、それを今の構成で実現するか、新しい構成が必要かを判断します。

一言でいうと：要求を見て、システム構成を変える必要があるか判断するStageです。
現在ST-03まで完了
今回ST-04の設計だけ
実装まだ行わない

まず、全体の流れです。

1 / CORE材料をそろえる

要求、現在の構成、組織ルールを固定します。

→
2 / AI構成への影響を調べる

変更が必要か、既存判断を使えるかを提案します。

→
3 / CORE根拠を検査する

参照、抜け、改ざん、権限を検査します。

→
4 / FIXED GRAPHST-05へ進む

AIではなくCoreが進めます。

入力と出力は、これだけです。

入力

  • ST-03で決めた要求
  • ST-01で確認した現在の構成
  • 組織やProjectのルール
→

出力

  • どの方法でST-04を通ったか
  • 新しい構成判断、または再利用した判断
  • 判断不要なら、その理由と根拠

Stage dispositionとは、作業方法の名前です。

難しい仕組みではありません。

「今回のST-04を、新しく作る・既存を使う・何もしない、のどれで処理するか」を表すラベルです。

execute新しく判断する
／
reuse既存判断を使う
／
not applicable構成判断がいらない

3つの違いを、実際の動きで説明します。

E

execute：新しい構成判断を作る

今の要求を満たすために、これまでにない構成判断が必要な場合です。

1Coreが入力を固定
2AIが選択肢を比較
3Coreが新しい判断を保存
4ST-05へ進む
結果：新しいArchitecture Decision JSONが作られます。
R

reuse：承認済みの構成判断をそのまま使う

必要な構成判断はありますが、すでに有効な判断が存在する場合です。

1既存判断を指定
2Coreがhashと承認を確認
3今の要求にも使えるか確認
4新規設計せずST-05へ
結果：新しい判断本文は作らず、使った既存判断を固定参照します。
N

not applicable：今回、構成判断をする必要がない

コードは変わっても、Component、API、Database、Providerなどの構成には影響しない場合です。

1AIが全要求を確認
2構成影響なしの根拠を提示
3Coreが抜けと参照を確認
4構成設計せずST-05へ
結果：Architecture Decisionは作らず、PlanとAuditへ理由・根拠を記録します。

具体例で見ると、違いは明確です。

EXECUTE新しいCacheを追加する

性能要求を満たすため、Cache方式、配置、影響を新しく決めます。

REUSE既存の認証方式を使う

会社で承認済みのIdP連携判断があり、今回もそのまま適用できます。

NOT APPLICABLEボタンの文字を変える

Login View内の文字だけを変えます。API、Database、配置、境界は変わりません。

3つのうち、誰が選ぶのですか？

AI

要求と現在の構成を調べ、execute／reuse／not applicableの候補と根拠を出します。

Core

固定ルールで根拠を検査し、正式なStage dispositionとしてPlanとAuditへ記録します。

人間

費用、リスク、Provider選択など、機械的に決められない場合だけ判断します。

AIだけでは決められない

AIは候補を出せますが、Stateを書き換えたり、次のStageを選んだりできません。

executeで新しく決める内容です。

1どこが変わるか

Component、API、Database、外部接続など。

2何を選ぶか

構成方式、通信方式、Providerやserviceなど。

3なぜ選ぶか

要求、制約、選択肢、良い点と悪い点。

4何に影響するか

データ、Security、費用、運用、既存Component。

5戻しやすいか

簡単に戻せるか、移行や損失が発生するか。

6要求とのつながり

どの要求IDのための判断か。

ST-04とST-05の境界です。

ST-04：大きな作り方

  • Componentの境界
  • APIやデータの接続方針
  • Providerやserviceの選択
  • 構成判断の理由と影響

ST-05：実装できる形へ分解

  • API fieldの詳細
  • Database schemaの詳細
  • 受入テスト
  • Boltの分け方と実装順
ST-04ではコードを作りません。ST-05でもまだコードを作りません。実装はST-06です。

現在の構成と、予定構成を混ぜません。

System Map現在の承認済み構成
→
ST-04変更予定を別に保存
→
ST-07承認後だけ現在へ反映
ST-04の予定を、現在のSystem Mapへ直接書き込みません。

保存されるものです。

すべて機械検査用のJSONです。HTMLは標準生成しません。

architecture-work-request.json　← Coreが固定した入力 current.json　　　　　　　　← どの方法でST-04を通ったか architecture-decision.json　← executeのときだけ作る新しい判断
reuseでは既存判断への参照を保存します。not applicableでは理由とEvidenceだけをPlan、Audit、current.jsonへ保存します。

人間へ質問する条件です。

質問せず進める

  • 構成影響が明らかにない
  • 承認済み判断をそのまま使える
  • 組織ルールで方法が決まっている
  • 容易に戻せる小さな判断

人間へ質問する

  • Providerや費用を選ぶ必要がある
  • データ移行や削除を伴う
  • SecurityやComplianceの例外が必要
  • 要求同士が衝突している

あなたに確認してほしいのは、3つだけです。

確認 1文字変更など、構成に影響しない変更はnot applicableでよいですか？

Architecture Decisionは作らず、理由と根拠だけを記録してST-05へ進みます。

確認 2承認済みの構成判断が使える場合はreuseでよいですか？

Coreがhash、承認状態、現在の要求との整合を検査し、新しい判断本文は作りません。

確認 3ST-04は大きな構成方針までにして、APIやDBの詳細はST-05でよいですか？

ST-04を細かくしすぎず、ST-05で実装可能な契約へ落とします。

3つとも問題なければ、「確認3点OK」と回答するだけで大丈夫です。

承認後の実装方法です。

RED

3種類の動作、根拠不足、改ざん、AIの遷移指定が失敗するテストを先に作ります。

GREEN

Work Request、Disposition検証、Architecture Decision保存を実装します。

CORE

CoreだけがPlan、Audit、Stateと固定ST-05遷移を更新します。

VERIFY

resume、Doctor、配布、指定サンドボックス、全体回帰を確認します。

このページは設計案です。
