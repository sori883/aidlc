Whole flow

ST-01の流れ

まず基準にするコードを固定します。次にSystem Mapの必要部分だけを確認し、そのrevisionを使ってCurrent Contextを作ります。

入力Receipt＋Design Brief対象と依頼を固定
→
Corebaselineを固定Repositoryごとのsnapshot
→
共有CodeKBSystem Mapを確認作成・再利用・Patch候補
→
今回のIntentCurrent ContextMap revisionを固定参照
System Mapがない固定した既存baselineから、最初のimmutable revisionを作ります。
System Mapがある今回に関係するEvidenceだけを現在snapshotと比較します。
Evidenceが同じ既存revisionをそのまま再利用します。
Evidenceが違う影響箇所をstaleにし、Patch候補を作ります。未承認変更は自動昇格しません。

ST-01で共有revisionへ確定できるのは、初回importと、同じcode baselineに対する観測範囲の追加だけです。コード内容を変えるPatch候補はST-07の承認を待ちます。

現在はIntent名しか永続化していません。ST-01を実装するときは、元の依頼を短文のDesign BriefとしてIntentへ保存し、再開後も同じ調査範囲を使えるようにします。

Two layers

確認はCoreとAIで分担します。

機械で比較できる事実と、構成の意味を読む作業を混ぜません。

1. Coreの検出と鮮度確認

Repository、commit、dirty状態、submodule、設定、外部情報をsource snapshotとして記録します。各Evidenceの変更を機械比較します。

2. AIの構成理解と対象調査

Design Briefに必要な範囲だけを調べます。System Mapの追加・修正はPatch候補として出し、Current Contextへ今回の事実と対象外をまとめます。

AIは調査の深さを選べます。ただし、対象Repository、使用できるStage、次の行き先は選べません。

No fixed slices

固定の切り口は使いません。

以前ご懸念いただいた、作業順や不要な実装を固定してしまう問題を避けます。

ST-01で固定しないもの
  • 画面、ユーザー行動、リスクという固定分類
  • フロントエンド、バックエンドという固定実装順
  • 技術レイヤーごとの作業スライス
  • 最初からProject全体を完全に調べること
  • 未観測部分をAIの推測で埋めること

System Mapは完成済みの設計図ではありません。Intentごとの観測結果をEvidence付きで蓄積する共有図です。実装順を決めるのはST-05のBolt Planです。

Cumulative system map

System Mapは、観測範囲を積み上げます。

小さなIntentで全Projectを読みません。分かった場所、分からない場所、古い可能性がある場所を区別します。

1

観測済み

Evidenceで確認できたComponent、Resource、接続。

2

未観測

存在する可能性はあるが、まだ調査していない範囲。

3

古い可能性

参照Evidenceが変わり、再確認が必要な範囲。

4

確認時点

いつ、どのRepository revisionを確認したか。

5

複数Provider

AWS、Azure、Vercelなどを共通categoryとcapabilityで表現。

6

必要時だけ図解

人間から指示されたときだけ、指定revisionのJSONからHTMLを都度生成。

Frontend ─配置─▶ web-hosting       ─提供─▶ Vercel Project
API      ─配置─▶ container-compute ─提供─▶ Azure Container Apps
Worker   ─配置─▶ function-compute  ─提供─▶ AWS Lambda
Database ─分類─▶ relational-db     ─提供─▶ Azure PostgreSQL

標準成果物はJSONだけです。HTMLは正本でも標準保存物でもありません。人間から依頼された場合だけ、coverage、freshness、unknownを読める表示として都度生成します。

Meaning of current

3種類の「現在」を混ぜません。

共有Map、作業中コード、Production実態は、それぞれ別物です。

System MapST-07で承認されたcode baselineの現在像。初回だけimported baselineから作成。
Intentの作業中差分dirty working treeやST-06の変更候補。承認前は共有Mapへ混ぜない。
Deployment Map実際にProductionで動いている構成。ST-08以降で別に扱う。
ST-01Orient

既存baselineを観測。初回Map作成と不足範囲の確認。

ST-04Architecture

将来構成を別Artifactとして決定。Currentへ混ぜない。

ST-06Build

実装結果からSystem Map Patch候補を生成。

ST-07Approval

承認後だけ新しい共有revisionへ昇格。

ST-08Release

Productionの実状態はDeployment Mapへ記録。

Storage

System MapはCodeKBに置きます。

Repository詳細をEvidenceとして使い、複数Repositoryを横断するSystem Mapを共有の集約Mapにします。

aidlc/spaces/<space>/
├── codekb/
│   ├── repositories/
│   │   ├── <frontend-repo>/
│   │   └── <backend-repo>/
│   └── system-map/
│       ├── baseline.json          ← 最新承認revisionへのポインタ
│       └── revisions/
│           └── 000001/
│               └── system-map.json
└── intents/
    └── <intent>/
        └── artifacts/
            ├── workspace-profile.json
            └── current-context.json

baseline.jsonはMap本体ではありません。revision、path、SHA-256だけを指します。過去revisionは上書きしません。HTML表示はこの保存領域へ自動生成しません。

Freshness

Map全体を1個のfingerprintで判断しません。

情報源ごとのsnapshotと、各要素が使ったEvidenceを結びます。

fresh参照Evidenceとsource snapshotが現在も一致しています。
staleEvidenceが変わりました。依存するentity・relationだけ再調査します。
unknown外部APIなどを確認できません。推測でfreshにはしません。
1

source snapshots

Repositoryごとのcommit・dirty状態・submodule。外部情報にはobserved_atと期限。

2

evidence refs

各entity・relationが参照するfile、path、SHA-256。

3

影響範囲

変わったEvidenceを参照する要素だけをstaleにする。

4

競合防止

Patchのbase_revisionが現行と違う場合、自動上書きせず再評価する。

What to capture

Current Contextに残す事実

Current ContextはIntent配下に置きます。使用したSystem Map revisionを固定し、後から共有Mapが変わっても過去の根拠を変えません。

1

Map固定参照

使用したrevision、path、SHA-256。

2

使用した要素

切り出したentity IDとrelation ID。

3

今回の追加事実

Design Briefに必要で、新しく確認した現在の振る舞い。

4

調査対象外

今回読まなかったRepository、機能、外部system。

5

Intent固有情報

作業中差分など、共有System Mapへ昇格しない情報。

6

未知と不足

確認できなかったこと。推測で埋めません。

Outputs

成果物は3組です。

機械検出、共有の全体図、Intent固有の現状を分離します。

Workspace Profile

workspace-profile.json
  • Coreが作成
  • Repositoryとtoolchainの事実
  • source snapshotを記録

System Map

system-map.json
  • CodeKBでimmutable revision管理
  • coverage・freshness・Evidence
  • 標準ではJSONだけを保存
  • 初回または同一code baselineの観測補完

Current Context

current-context.json
  • Intent配下に保存
  • Map revisionとSHA-256を固定
  • 対象外とIntent固有情報を明示

schema_versionとrevisionは別fieldです。ファイル名のr1で両方を表しません。

Strict contract

JSONにするだけでは安全になりません。

Coreが厳格なContractを検証し、合格したPatchだけを新revisionへ昇格します。

1

Schema

未知fieldを拒否。schema_versionとrevisionを分離。

2

IDと参照

entity IDの重複と、存在しないentityへのrelationを拒否。

3

Relation

種別をenum化し、自由な関係名を許可しない。

4

Evidence

path・SHA-256を必須化し、Repository境界外を拒否。

5

時制

Current、planned、working差分の混在を拒否。

6

安全

秘密情報を保存しない。依頼によりHTMLを生成する場合は必ずescape。

Patchはbase_revisionを持ちます。別Intentが先に更新していた場合、自動上書きせず新しいbaselineで再評価します。

Responsibility

誰が何を決めるか

ST-01の完了はAIの自己申告では決まりません。

Core

baselineとsnapshotを固定し、Schema・Evidence・競合を検証して、固定Graphで遷移します。

AI

必要範囲を観測し、Map Patch候補とIntent固有のCurrent Contextを作ります。

人間

HTML図を読みます。初回baseline、対象、確認不能な外部情報、承認を判断します。

Disposition rules

execute・reuse・not_applicable

小さな変更では調査を小さくします。Stageそのものを重くしません。

execute初回Mapを作る、必要Evidenceがstale、またはCurrent Contextを新しく作る場合。
reuse必要なentity・relationのEvidenceがfreshで、既存Contextの調査範囲も一致する場合。
not_applicable通常は使いません。Greenfieldでも「観測済み構成なし」という最小revisionを記録します。

文字変更の例では、対象fileと現在の文字、その参照関係だけを確認します。Project全体の解析は行いません。

Stop conditions

推測が必要なら停止します。

分からないままCurrent Contextを完成扱いにしません。

対象が曖昧複数Repositoryのどれを調べるかDesign Briefから決められない。
Evidence不足重要な主張にfile、manifest、command結果などの根拠がない。
baseline不明dirty working treeしかなく、共有Mapの基準にする承認済みcodeを固定できない。
Access不可必要なRepository、submodule、外部情報を読めない。
鮮度を確認不能必要な外部APIや設定の根拠を確認できず、該当要素をfreshと証明できない。
revision競合Patch作成中に別Intentがbaselineを更新した。
Brief不足調査範囲を絞れず、Project全体を読むしかなくなる。

Boundary

ST-01では決めないこと

CurrentとFutureを混ぜないための境界です。

  • 目的、優先順位、成功基準はST-02
  • 機能要求、NFR、制約はST-03
  • 採用する将来ArchitectureはST-04。System Mapへ混ぜない
  • 実装順、依存DAG、Bolt PlanはST-05
  • Application codeの変更とMap Patch候補はST-06
  • 変更後Mapの共有baseline昇格はST-07
  • Productionの実状態はST-08のDeployment Map

TDD implementation

承認後の実装順

ST-00と同じく、失敗するテストを先に書きます。ST-02には着手しません。

1

RED

stale誤再利用、revision競合、壊れたrelation、未承認codeの自動昇格を先に失敗させます。

2

Contract

Workspace Profile、System Map、Patch、baseline pointer、Current Contextのschemaを作ります。

3

Source scan

Repository・外部情報ごとのsnapshotを作り、Evidence単位でfreshnessを判定します。

4

Map revision

初回Mapと同一baselineの観測補完だけを確定し、コード変更Patchは承認待ちにします。

5

Context・Verifier

Intent配下のContextへrevisionとSHA-256を固定し、合格時だけST-02へ進めます。

6

GREEN・回帰

unit、resume、failure、Codex、native、Sandbox、release:checkを確認します。

Decision requested

実装前に確認する8点

次を承認いただいたら、ST-01だけをTDDで実装します。

1. 元の依頼を短いDesign BriefとしてIntentへ保存する。
2. System MapをCodeKB内の累積型・観測Mapとする。
3. 初回はimported baseline、以後は承認済みbaselineを共有する。
4. source snapshotとEvidence単位でfreshnessを判定する。
5. immutable revisionとbaseline.json pointerを使用する。
6. Current ContextはIntent配下でMap revisionを固定参照する。
7. working、planned、Productionを共有System Mapへ混ぜない。
8. System MapはJSONだけを標準保存し、HTMLは人間の指示時だけ安全に都度生成する。
