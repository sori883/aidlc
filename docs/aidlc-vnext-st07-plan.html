AI-DLC vNext / M5 / ST-07 PLAN

人間が実物を見て、承認か戻り先を確定する。

ST-07 Human Feedback & Approvalは、ST-06の完成候補を人間が確認するStageです。AIは説明と分類案を作れますが、承認も行き先も決めません。

入力Runnable Candidate
人間の選択承認 / Feedback
判断不能停止して確認
承認後固定ST-08

何をするStageですか？

1 / CORE確認対象を固定

Candidate、要求、合格条件、EvidenceのSHA-256を固定します。

→
2 / HUMAN実物を確認

動作、見た目、使い心地、既知制約を確認します。

→
3 / CORE決定を検証

承認かFeedbackかを厳格JSONとして記録します。

→
4 / FIXED GRAPH進むか戻る

承認ならST-08。Feedbackなら許可済みのStageだけへ戻ります。

ST-07は「AIに次を相談するStage」ではありません。人間の明示的な判断を、Coreが固定Graphへ接続するStageです。

人間が見るものは、1つのReview画面です。

JSONを直接読ませません。Coreが固定したReview Manifestから、短文の静的HTMLを生成します。

WHAT

何が変わったか

Repository、変更file、基点revision、候補revisionを表示します。

WHY

何を満たすべきか

ST-03の要求とST-05の受入条件を短文で表示します。

EVIDENCE

機械検証の結果

ST-06で合格したtestとVerifier Evidenceを表示します。

TRY

どう確認するか

localhostの起動方法、確認手順、必要な試験データを表示します。

HUMAN CHECK

人間だけの確認

見た目や使い心地など、human-at-st07項目を表示します。

LIMITS

まだ対象外のこと

既知制約、未確認事項、今回変えない範囲を表示します。

System MapのHTMLとは扱いが違います。System Mapは指示時だけ生成しますが、このReview HTMLは人間の承認Gateそのものなので、ST-07のexecute時に標準生成します。

入力と出力

種類Artifact初心者向けの意味
入力Build CurrentST-06をexecute／reuse／not_applicableのどれで通ったかです。
入力Runnable Candidate全Boltと統合検証に合格した完成候補です。not_applicable時はありません。
入力Requirements + Build Contract「何を満たすか」と「どう合格させるか」の承認済み正本です。
入力Checkpoint + Verifier Evidenceどの変更と機械検証を通ったかを示す証拠です。
途中Review Manifest + Review HTML確認対象を固定するJSONと、人間が読む画面です。
出力Human Decision承認、またはFeedbackの種類と理由を記録した人間の判断です。
承認時Accepted Candidate候補SHA-256とsource revisionへ固定した、ST-08へ渡す承認済み成果です。
Feedback時Feedback Currentどの正本と比較し、どこから見直すかを固定した記録です。

Feedbackは4種類だけです。

人間には専門用語だけを選ばせません。次の質問で、何を見直す必要があるかを明示します。

requirements_changed

目的、対象範囲、成功条件、制約そのものを変えたい。

ST-03へ
architecture_impact

Component境界、API、データ流、Providerなど、構成判断を変える必要がある。

ST-04へ
build_contract_impact

受入条件、Verifier、変更対象path、Boltの分け方や順番を変える必要がある。

ST-05へ
candidate_defect

要求も構成も合格条件も変えず、実装だけを直せばよい。

ST-06へ
「ログインできるはずなのに動かない」はST-06です。「ログイン後に二要素認証も必須にしたい」は要求変更なのでST-03です。

複数の指摘がある場合も、行き先は1つです。

人間が各指摘への影響を確認します。Coreは、必要な見直し範囲が最も広いStageを機械的に選びます。

ST-03要求を見直す
ST-04構成を見直す
ST-05作り方を見直す
ST-06実装だけ直す
例：実装不具合と要求変更が同時にある場合はST-03へ戻ります。ST-04〜ST-07を再評価するため、不具合修正も取りこぼしません。分類が曖昧なら、Coreは勝手に選ばずST-07で停止します。

ST-03との矛盾を残しません。

人間が変えたいこと

  • Feedbackを対象要求IDへ結び付ける
  • 「要求を変える」か「既存要求への不具合」かを明示する
  • 必要なら複数の影響分類を確認する

Coreが必ず比較するもの

  • ST-03 Requirements revisionとSHA-256
  • ST-04 Architecture Current
  • ST-05 Build Contractと受入条件
  • ST-06 CandidateとVerifier Evidence

ST-03へ戻る

ST-03〜ST-07のCurrentをstaleにし、要求から再評価します。

ST-04へ戻る

ST-04〜ST-07をstaleにし、構成判断から再評価します。

ST-05へ戻る

ST-05〜ST-07をstaleにし、合格条件とBoltを再作成します。

ST-06へ戻る

ST-06〜ST-07をstaleにし、承認済みContract内で修正します。

過去は消さない

immutable revision、判断、EvidenceはAuditのため保存します。

Currentだけ切り替える

古い成果物を正本として再利用しないよう、参照を更新します。

承認は「その候補だけ」に効きます。

画面を見た後でコードが変わっても、古い承認を使えないようにします。

承認に固定する値

Runnable Candidate SHA-256Review Manifest SHA-256Requirements revision / SHA-256Architecture Current SHA-256Build Contract revision / SHA-256Repositoryごとのcandidate revision
→

Accepted Candidate

すべて一致した場合だけ作ります。

approval_refrunnable_candidate_refaccepted_source_revisionssystem_map_revision_ref
承認後に1 byteでもReview ManifestやCandidateが変わればSHA-256が変わります。Coreは承認を無効として扱い、再確認を要求します。

System Mapは、承認後だけ更新します。

CANDIDATE候補コードを観測

AIが変更部分だけを読み、Map Patch候補を作ります。

→
COREEvidenceを検証

candidate revision、base revision、ID、relationを検査します。

→
HUMAN完成候補を承認

Patch単独ではなく、同じ候補への承認へ結び付けます。

→
CODEKB新revisionへ昇格

承認後だけ共有System Mapのbaselineを切り替えます。

System Mapの正本は引き続きJSONだけです。ここでもSystem Map HTMLは自動生成しません。Review HTMLへは、変更された構成の短い要約だけを表示します。

AI・人間・Coreの役割

AIができること

  • 変更内容を短く説明する
  • 確認手順と既知制約を整理する
  • Feedback分類案を理由付きで出す
  • System Map Patch候補を作る

人間だけが決めること

  • 実物を受け入れるか
  • human-at-st07項目の合否
  • 要求を変える意思があるか
  • Feedbackの影響分類

Coreだけができること

  • 確認対象のSHA-256を固定する
  • Decision JSONを検証・保存する
  • 複数指摘の戻り先を機械決定する
  • Plan、State、Audit、Currentを更新する

誰も勝手にできないこと

  • AIだけで承認する
  • 固定GraphにないStageへ戻る
  • Feedback中に候補コードを書き換える
  • ST-07から外部Releaseする

3つの処理方法

execute

新しく人間が確認する

新しいRunnable Candidateがあり、Review HTMLを作って明示的な判断を待ちます。

reuse

同じ判断を再開する

同じIntentで、Candidateと全参照SHA-256が完全一致する保存済み判断だけを再利用します。別Intentへ承認を流用しません。

not_applicable

確認する候補がない

ST-06がnot_applicableでRunnable Candidateがない場合だけ、ST-05の承認をEvidenceにCoreが決定します。Accepted Candidateは作りません。

保存先の案

artifacts/review/review-manifest.json ← 確認対象の正本 artifacts/review/review.html ← 人間向けの静的画面 artifacts/review/system-map-patch-candidate.json ← 変更構成がある場合 artifacts/review/human-decision.json ← 承認またはFeedback artifacts/review/accepted-candidate.json ← 承認時だけ artifacts/review/feedback-current.json ← Feedback時だけ artifacts/review/current.json ← ST-07の確定結果
JSONは厳格schemaで検証します。未知field、参照切れ、SHA-256不一致、秘密情報、Repository外path、HTML未escape文字を拒否します。

TDDで作る範囲

CONTRACT厳格JSON

Manifest、Decision、Accepted Candidate、Feedback Currentをfail closedで検証します。

REVIEW安全な静的HTML

短文、確認手順、human verifier、既知制約、escapingを試験します。

APPROVALSHA-256固定

改ざん、古い候補、別Intent、source revision driftを拒否します。

FEEDBACK4本の固定edge

単一・複数・曖昧なFeedbackとCurrent失効範囲を試験します。

SYSTEM MAP承認後だけ昇格

base revision競合、Evidence、candidate revisionを検証します。

RECOVERY中断再開

Plan、State、Audit、Doctor、Codex／native配布まで確認します。

今回まだ作らないもの

ST-08のRelease、deploy、Production接続、外部環境への変更、ST-09のOutcome評価は含めません。ST-07の承認は「完成候補を受け入れる」判断であり、「Productionへ出してよい」という権限ではありません。
