AI-DLC vNext / M3 / ST-05 DESIGN

ST-05は、AIへ渡す「実装の契約書」を作ります。

何を変えるか、どう合格を確認するか、どのBoltから実装するかを固定します。ここではまだコードを作りません。

StageST-05 Build Contract
主な成果物Build Contract JSON
人間の確認ST-06前に1回
次の固定StageST-06

一言でいうと。

ST-04までは「何を、どの構成で作るか」を決めました。ST-05は、それをAIが迷わず実装できる作業契約へ変換します。

入力

要求と構成判断
  • 何を満たすか
  • 何を変えないか
  • 構成変更があるか
→

出力

AIが実装できる契約
  • 変更箇所と詳細
  • 合格条件と確認方法
  • Boltの依存関係と順序

ST-05の流れは、5手です。

1 / CORE入力を固定

Requirements、Architecture、Current、PolicyをSHA-256で固定します。

→
2 / AI契約を提案

変更契約、受入条件、Verifier、Bolt DAGを提案します。

→
3 / CORE機械検査

抜け、循環、依存関係、危険なcommandを検査します。

→
4 / HUMAN一度だけ承認

短いHTMLを読み、承認または修正を伝えます。

→
5 / FIXED GRAPHST-06へ

承認後だけCoreが進めます。

人間の確認はBoltごとではありません。AIが自走を始める直前に、Build Contract全体を1回確認します。

Build Contractには、4つ入ります。

1

変更契約

どのRepositoryの、どのpathやinterfaceを、どう変えるか。

2

受入条件

何が起きたら、そのRequirementを満たしたと言えるか。

3

Verifier

test、runtime確認、artifact確認など、合格を調べる方法。

4

Bolt Plan

作業単位、依存関係、統合条件、止める条件。

Build Contractが、これまで呼んでいたDesign Contractの「実装可能な完成形」です。別々の正本を作らず、1つのimmutable JSONへまとめます。

Boltは「依存関係付きの作業単位」です。

画面、フロントエンド、バックエンドなどの固定分類ではありません。変更内容に合わせてAIが提案し、Coreが依存関係を検査します。

BOLT-001APIを先に作る
→
BOLT-002APIに依存する画面を作る
→
統合確認全体の受入条件を実行

依存する場合

depends_onで順序を固定します。Coreは前のBoltが完了するまで次をreadyにしません。

独立している場合

依存とpath競合がなければ同じbatchとして並行実行できます。batchはCoreがDAGから計算します。

v2の「必ずB1をwalking skeletonにする」規則は持ち込みません。必要なら縦にまとめたBoltを提案できますが、毎回同じ分け方を強制しません。

依存関係を、二重に確認します。

変更契約の依存

  • 画面ContractがAPI Contractへ依存
  • Migrationが新しいschemaへ依存
  • Testが実装Contractへ依存

Boltの依存

  • 別BoltのContractへ依存するならBoltも依存
  • 同じBolt内なら追加Edgeは不要
  • 循環したらCoreが拒否
依存するContractを別Boltへ入れたのに、Boltのdepends_onがない場合はCoreが止めます。フロントエンドを早く作りすぎる問題を防ぎます。

Requirementからtestまで、つながります。

REQ-F-001何を満たすか
→
CHG-001何を変えるか
→
AC-001どうなれば合格か
→
BOLT-001どこで実装・確認するか

Coreが必ず確認

  • 全Requirementにbuild影響判定がある
  • 影響ありのRequirementに変更契約がある
  • 全ConstraintとInvariantに受入条件がある
  • 全受入条件にVerifierがある
  • 全変更契約がBoltに所属する

Coreが拒否

  • 根拠のない作業
  • testできない「良い感じにする」
  • 循環したBolt DAG
  • 並行Boltのpath競合
  • shell文字列やRepository外path

Verifierも契約として固定します。

ST-05ではVerifierを実行しません。ST-06が安全に実行できる形かを検査して保存します。

A

command

shell文字列ではなくargv配列。cwdはRepository内だけ。

B

runtime

起動、HTTP、browser操作など、実物の動きを確認。

C

artifact

JSON schema、生成物、coverageなどを確認。

D

human at ST-07

見た目や使い心地など、人間にしか判断できない項目。

ST-06用の機械VerifierがないRequirementは、理由と人間の例外承認が必要です。秘密値やcredentialはBuild Contractへ保存しません。

小さな変更は、1 Boltで短くします。

例：文字をAからBへ変更

  • 変更契約：1件
  • 受入条件：変更後の表示と既存動作
  • Verifier：既存testまたは小さなtest
  • Bolt：1件

例：APIと画面を追加

  • API Contract
  • 画面Contract
  • API → 画面の依存関係
  • 統合Verifier
資料の量を先に決めません。Requirementと依存関係が少なければ、Build Contractも短くなります。

ST-05にも3つの処理方法があります。

execute

新しい契約を作る

通常の実装変更です。小さな変更なら1 Boltの短いBuild Contractになります。

reuse

既存契約を使う

Requirements、Architecture、Currentが一致し、既存契約のSHA-256を再確認できる場合だけです。

not_applicable

Build作業がない

全Requirementがbuild影響なしの場合だけです。機能変更や修正が1つでもあれば使えません。

3方式のどれでも、人間はST-06へ進む前に最終内容を1回確認します。AIだけでBuild Contractを承認できません。

人間は、JSONを直接読まなくてよい設計です。

CoreがProposalを検査した後、承認用の短いHTMLを自動生成します。

artifacts/build-contract/build-contract-work-request.json artifacts/build-contract/review/build-contract-candidate.json artifacts/build-contract/review/build-contract-review.html ← 人間向け artifacts/build-contract/revisions/000001/build-contract.json ← 承認後の正本 artifacts/build-contract/current.json
JSONが正本です。HTMLは検査済みJSONからCoreがescapingして生成する閲覧用です。人間のApprovalはHTMLではなく、Candidate JSONのSHA-256へ結び付けます。

承認と修正を、はっきり分けます。

承認する

  • 人間が明示的に「承認」と伝える
  • Coreがhuman-decisionを記録
  • Candidate SHA-256を固定
  • immutable revisionを作成
  • 固定GraphでST-06へ進む

修正する

  • 人間が変更点を短文で伝える
  • StateはST-05のまま
  • AIがProposalを修正
  • Coreが再検査してHTMLを更新
  • 承認されるまで遷移しない
AIはProposal内へapproved: trueや人間権限を入れられません。明示的な人間メッセージを受けたHarnessだけがApproval commandを実行します。

Core Directiveに「承認待ち」を追加します。

通常のAI作業と、人間が見る場面を混同しないためです。

workAIの提案待ち

Work Requestを返します。

→
approval人間の確認待ち

Candidateとreview HTMLを返します。

→
advancedST-06へ進行

承認Evidenceを返します。

State schemaへ新しい一時状態を増やさず、承認待ちはST-05のparkedとApproval Directiveで表現します。

Stageの境界です。

ST-04

大きな構成方針を決めます。現在像と将来案を分けます。

ST-05

詳細な変更契約、受入条件、Verifier、Bolt DAGを固定します。

ST-06

CoreがreadyなBoltを指定し、AIがTDD、実装、実行、修正を反復します。

ST-05ではsource codeやtest codeを作りません。ST-06の実行方法を契約として決めるだけです。

人間へ戻す条件です。

価値判断

どちらの体験、費用、互換性を優先するか。

不可逆・危険

削除、migration、外部副作用、Security例外。

仕様矛盾

Requirement、Architecture、Policyが両立しない。

検証不能

合格条件を機械Verifierへできず、例外判断が必要。

DAG不成立

循環やpath競合を解消する設計判断が必要。

最終Approval

AI自走前のBuild Contract全体確認。

実装時のTDD範囲です。

Contract test

未知field、秘密field、ID重複、3方式の相互排他。

Coverage test

Requirement、Constraint、Invariant、受入条件の抜け。

DAG test

循環、dangling dependency、path競合、Core batch計算。

Verifier test

argv、cwd、Repository境界、Policy allowlist。

Approval test

未承認遷移、改ざん、古いCandidate、修正後の再承認。

Recovery test

Candidate、HTML、Approval、revision保存途中からの再開。

実装前に確認するのは、3点です。

確認 1ST-06の自走前に、Build Contract全体を人間が1回承認する形でよいですか？

Boltごとの承認は置きません。修正の場合だけST-05内で再レビューします。

確認 2Boltは固定Sliceや必須walking skeletonを持たず、依存関係DAGで順序を決めてよいですか？

バックエンド→フロントエンドのような必要順序をCoreが強制できます。

確認 3JSONを正本にしつつ、ST-05だけは承認用HTMLをCoreが毎回自動生成してよいですか？

System Map HTMLは生成しません。Build Contractの人間レビュー専用HTMLだけです。

この時点では、まだ実装しません。

3点の確認後、ST-05 Contract、Work Request、Candidate、DAG validator、review HTML、Approval、固定ST-06遷移をTDDで実装します。
