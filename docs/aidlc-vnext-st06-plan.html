AI-DLC vNext / M4 / ST-06 PLAN

AIは作る。Coreは順番と合否を握る。

ST-06 Build & Convergeは、承認済みBuild Contractを実際のコードへ変えるStageです。Coreが実行可能なBoltを1つ指定し、AIはそのBoltだけを実装・検証・修正します。

入力承認済み契約
作業単位1 Boltずつ
通常の人間Gateなし
成功時ST-07へ

何をするStageですか？

1 / COREready Boltを指定

依存Boltが完了したものから、Coreが次の1つを選びます。

→
2 / AI実装と修正

指定pathだけを変更し、必要なtestも作ります。

→
3 / CORE独立して検証

diffを確認し、承認済みVerifierをshellなしで実行します。

→
4 / FIXED GRAPH全Bolt後にST-07

一部成功では進みません。統合検証まで成功した場合だけです。

3つのループを混ぜません。

1

AI内部loop

今のBoltを実装 → 検証 → 修正します。ST-06の内側です。

2

Bolt loop

Coreが完了を記録し、依存関係から次のBoltを指定します。AI内部loopの外側ですが、ここもST-06の中です。

3

Outcome loop

人間が完成物を評価し、要求や次のIntentへ返します。ST-07〜ST-09で扱います。

AIが「次は何を作ろう」と自由に決める余地はありません。今のBoltの実装方法だけを選べます。

入力と出力は、こうなります。

種類Artifact初心者向けの意味
入力Build Contract Currentexecute／reuse／not_applicableの確定結果です。
入力Build Contract + Human Approval何を作り、どう合格させるかを人間が承認した正本です。
入力Effective Policy試行上限、禁止操作、作業の分離方法などのProjectルールです。
途中Build Session現在のBolt、完了Bolt、試行回数をCoreが記録します。
途中Attempt Checkpoint + Verifier Evidence各試行で何を変え、何が成功・失敗したかの証拠です。
出力Runnable Candidate全Boltを統合し、ST-07で人間が確認できる完成候補です。

1回のBoltで起きること。

PREPARE

作業場所を分ける

Coreが基点revisionを固定し、対象Git RepositoryにBolt専用worktreeを作ります。

IMPLEMENT

AIがコードを変更

Work RequestにあるChange Contract、受入条件、target pathだけを扱います。

VERIFY

Coreがdiffとtestを検査

対象外変更を拒否し、Verifierをargv配列で実行してEvidenceを保存します。

RETRY

失敗なら同じBoltを直す

失敗EvidenceをAIへ返します。次のBoltへ逃げることはできません。

INTEGRATE

成功Checkpointを統合

成功した変更だけを基準branchへ統合し、後続Boltをreadyにします。

CONVERGE

最後に全体検証

全Bolt後にIntegration Contractを検証し、Runnable Candidateを確定します。

AIとCoreの権限を分けます。

AIができること

  • 指定Boltのコードとtestを作る
  • 失敗Evidenceから同じBoltを修正する
  • 実装内容と観測結果をCheckpoint候補として説明する
  • Contract矛盾や重大リスクを報告する

Coreだけができること

  • ready Boltを決める
  • 試行番号と予算を管理する
  • 実diff、対象path、source revisionを検査する
  • Verifierを実行してpass／failを決める
  • Checkpoint、Audit、Stateを保存する
  • ST-07へ進める

自動修正を止める条件。

同じ失敗が3回

failure signatureが変わらなければ、改善していないと判断します。

Policyの試行上限

Bolt別・全体のattempt上限に到達したら止まります。

Contract外の変更

承認されていないsourceやpathへ変更が出たら拒否します。

基点が変わった

人間や別作業がRepositoryを変更し、固定snapshotと一致しなくなった場合です。

重大・不可逆な操作

deploy、外部送信、破壊的migration、秘密情報が必要なら人間へ戻します。

契約そのものが矛盾

実装では解決できないRequirements／Architecture／Build Contract矛盾です。

通常のtest失敗は人間へ聞かず自動修正します。人間へ戻すのは、実装技術では解けない判断・権限・安全性の問題だけです。

3つの処理方法。

execute

Boltを製造する

承認済みBuild Contractがあり、新しいコード変更が必要です。

reuse

完成候補を再利用する

同じBuild Contractとsource snapshotに結び付いた既存Runnable Candidateがある場合です。

not_applicable

製造しない

ST-05がnot_applicableでBuild Contract本体がない場合だけ、Coreが決定的に認めます。

保存先の案。

artifacts/build/build-session.json ← Coreの現在位置 artifacts/build/bolts/BOLT-001/work-request.json ← AIへ渡す今の作業 artifacts/build/bolts/BOLT-001/attempts/000001/checkpoint.json artifacts/build/bolts/BOLT-001/attempts/000001/verifiers/VER-001.json artifacts/build/runnable-candidate.json ← 全Bolt成功後 artifacts/build/current.json ← ST-06の確定結果
ソースコードの正本はRepositoryです。Intent配下へコードを複製せず、revision・変更file・SHA-256・Verifier Evidenceを記録します。

ST-06の前に、ST-05を少し補強します。

ST-06は実際にコマンドを実行します。候補SHA-256に含まれているだけでは、人間が安全性を読みやすいとは限りません。

Review HTMLを補強

  • Verifierの実行argv
  • 実行cwdとsource
  • 変更対象path
  • 外部作用がないこと

Verifierを構造化

  • command: argv、timeout、終了条件
  • artifact: pathと機械判定
  • runtime: 起動commandとlocalhost probe
  • human-at-st07: ST-07へ明示的に延期
これはST-05の意味を変える作業ではありません。ST-06が安全に実行できる情報を追加する互換的な補強として、同じTDD実装に含めます。

実装前に確認してほしい4点。

以下を採用する案です。すべて「はい」であれば、この設計をTDD実装します。

初期版は1 Boltずつ実行する

DAGは並列可能性を保持しますが、Codex初期版はCoreが決定的に1つずつ指定します。

提案: はい。安全な直列実行から始める。

通常はBoltごとの人間承認を置かない

test失敗はAIが同じBolt内で直します。価値判断・重大リスク・停止条件だけ人間へ戻します。

提案: はい。自律収束を基本にする。

execute対象はGit Repositoryを必須にする

回復可能なworktreeとrevisionを保証します。非Git directoryのexecuteは勝手に直接編集せず、Git初期化を人間へ依頼して停止します。not_applicableは影響を受けません。

提案: はい。回復不能な直接編集を避ける。

同じ失敗3回を標準停止条件にする

MemoryのBuild Policyに厳しい上限があればそちらを優先します。時間・費用上限もPolicyがあれば追加します。

提案: はい。無限修正を防ぐ最低限の既定値にする。

TDDで作る範囲。

CONTRACT厳格JSON

Session、Work Request、Attempt、Evidence、Runnable Candidateをfail closedで検証します。

SCHEDULERCore ready判定

DAG、完了Bolt、固定順から、次の1 Boltだけを決定します。

CONVERGENCEfail → retry → pass

実command verifier、failure signature、3回停止、中断再開を試験します。

ISOLATIONGit worktree

対象path、diff、merge、競合、基点drift、複数Repositoryを試験します。

INTEGRATION全Bolt後だけCandidate

一部成功では生成せず、統合Verifier成功後だけST-07へ進みます。

DISTRIBUTIONCodex／native

Directive、CLI、Doctor、Bundle、指定Sandboxまで確認します。

今回まだ作らないもの。

ST-07の人間Feedbackと最終Approval、ST-08のRelease／deploy、ST-09のOutcome評価、複数Boltの同時並列実行は含めません。ST-06が作るのは、全Boltを統合した「人間に見せられる候補」までです。
