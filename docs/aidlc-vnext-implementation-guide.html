30秒で理解する

AI-DLCは、AIが自由な順番で開発するのを防ぎ、固定された10個の工程に沿って作業させる仕組みです。 「Stage（ステージ）」は、目的整理、設計、実装、レビュー、リリースなどの工程を表します。

Codex Hookは、その仕組みを会話やTool実行の境界でも支える追加機能です。 「Hook（フック）」とは、セッション開始、Tool実行前後、Agent終了などの決まったタイミングで自動実行される小さな処理です。

  • Core開発の正しい順番と状態を管理
  • Agent決められた役割で成果物を提案
  • Hook境界を観測・検査・保護
  • Human重要な判断を最終決定

1. AI-DLC本体として実装したもの

会話だけに頼らず、同じProjectを再開しても「現在どこまで進んだか」を機械的に確認できるCoreをGoで実装しました。

FIXED WORKFLOW

固定された10 Stage

工程の追加・削除・並べ替えはAIに任せません。CoreがCatalogとGraphを正本として管理します。

PERSISTED STATE

永続化された状態と計画

現在のStage、Plan revision、成果物参照、監査記録をProject内へ保存します。会話が圧縮されても再開できます。

HUMAN AUTHORITY

人間が握る重要判断

設計、Build Contract、レビュー、リリース、成果判定などは、人間の明示的な確認を通して適用します。

2. Codex向けに実装した7つのHook機能

Auditだけではありません。観測から始め、再開、変更保護、人間承認、機械検査、Agent返却、稼働診断までを段階的に実装しました。

01

ST-HK-01

Hook Audit

セッション、Tool前後、サブエージェント、会話圧縮、Stopなど10種類のイベントをメタデータとして記録します。普通の質問は監査へ記録しません。

主な入口: hook record / hook turn / hook status

02

ST-HK-02

Context Injection

セッション開始やAgent開始時に、永続化された現在地、Stage Contract、担当候補、再開コマンドを追加コンテキストとして渡します。

主な入口: hook inject

03

ST-HK-03

PreToolUse Guard

Tool実行前に変更先を検査します。Core管理領域への直接変更や、ST-06で合意された対象外への変更を実行前に拒否します。

主な入口: hook guard

04

ST-HK-04

Human Input Receipt

レビュー対象を固定し、生成済みの確認行を人間が送った事実をReceiptとして結び付けます。未解決の判断がある間はStopで待機させます。

主な入口: human-gate / hook receipt / hook freeze

05

ST-HK-05

Deterministic Sensors

Go整形、JSON構文、承認対象ファイルのSHA-256一致を、AIの主観ではなく決定的なGo処理で確認します。

主な入口: hook sensor / sensor

06

ST-HK-06

SubagentStop Result Control

Stage Agentの最終結果、役割、Skill、変更範囲、ファイルSHA-256を検証します。不正な返却は1回だけ訂正を求めます。

主な入口: hook subagent / delegation receipt

07

ST-HK-07

Hook Health & Doctor

イベントが届いたか、各handlerが動いたか、Sensorが対象に一致して実行されたか、Agent Receiptが有効かを分けて診断します。設定欠落・重複・改ざんはerror、未観測はwarningまたはinfoとして扱います。

主な入口: hook status / sensor status / doctor check

普通の質問は、Hook Journalへ記録しません。

UserPromptSubmitでは、OSの一時領域にある空のセッションマーカーだけを上書きします。質問本文、Session ID、Turn ID、質問回数は永続化しません。生成済みの/aidlc-confirmが完全一致した場合だけ、別のReceiptとして残します。

3. できることと、できないこと

Hookは強力ですが、AI-DLC全体の決定権を持ちません。この線引きを実装と設計文書の両方で固定しました。

Hookが行うこと

  • Codex lifecycleのメタデータを観測する
  • 永続化済みの正しい現在地を再提示する
  • 危険な変更をTool実行前に拒否する
  • 人間入力と固定済みレビュー対象を結び付ける
  • 決定的な検査結果と稼働状況を記録する

Hookに任せていないこと

  • Stageの追加、並べ替え、勝手な遷移
  • 人間に代わる承認やリリース判断
  • 会話内容や秘密情報の保存
  • Agentの役割を推測して権限を増やすこと
  • ReceiptをCore受入れや法的本人署名とみなすこと
記録 主な場所 意味 権限
Core Audit audit/*.md Stage処理やCore判断の正式な履歴 正本
Hook Journal hook-audit/*.jsonl 通常質問を除くCodex境界イベントの観測証拠 非権威の観測記録
Human Turn Marker OSの一時領域 最新の人間ターンがあったことだけを示す空ファイル 一時的な制御情報
Receipt / Health artifacts/配下 人間入力、Agent返却、handler稼働などの検証材料 用途を限定した証拠

4. 配布と導入もGoで実装

利用先にGo、Node.js、Bunを要求しないよう、5種類のネイティブCLI、Installer、Manifest、Checksumをまとめて生成します。

  1. Release candidateを生成
    macOS、Linux、Windows向けのCLIとInstallerをローカル出力します。
  2. 配布物を検証
    ファイルサイズ、SHA-256、実行形式、Go build情報、native smokeを検査します。
  3. 安全にProjectへ導入
    競合、改ざん、危険なpath、symlinkを拒否してからCodex用ファイルを配置します。
  4. CodexでHookを信頼
    導入後はCodexの/hooksで内容を確認し、新しいSessionで実発火を確認します。
# 導入後の基本確認
./.codex/tools/aidlc --version
./.codex/tools/aidlc graph validate
./.codex/tools/aidlc workspace init .
./.codex/tools/aidlc intent birth . "最初のIntent"
./.codex/tools/aidlc next .

# Hookと全体の診断
./.codex/tools/aidlc hook status .
./.codex/tools/aidlc doctor check .

5. テスト内容の概要

詳細なテストケース一覧ではなく、「どの範囲を確認しているか」だけをまとめます。

機能と境界

各Hook、Core、Installerが正常系と拒否系で契約どおり動くこと、秘密になり得る本文を記録しないことを確認します。

並行処理と耐障害性

複数handlerや記録処理が重なってもStateやEvidenceを壊さないことを、race testを含めて確認します。

Go Quality Gate

gofmt、go vet、go test、native buildを実行し、Go 1.26.4で検証します。

配布経路

5 TargetのRelease candidate、ZIPの完全性、一時ProjectへのInstaller導入、導入後CLIとHook診断までを通して確認します。

テスト結果を読むときの注意
Unit testが成功しても、CodexがProject-local Hookを信頼して実際に読み込んだ証明にはなりません。 導入先では/hooksの確認、新しいSessionでの実発火、hook statusとdoctor checkの確認が必要です。
